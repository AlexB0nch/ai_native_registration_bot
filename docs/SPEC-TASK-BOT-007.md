## Goal

Владелец рассылает сообщение всем, кто записался на практикум, командой боту, без скриптов:
`/broadcast_practicum <текст>` → предпросмотр с числом получателей → кнопка «Отправить» → отчёт.
Решение владельца от 30.10.2026 (первый случай — ссылка на событие в Яндекс Календаре за день до практикума).

Это только ручная команда. Автоматические приглашения за 24 часа и за час — TASK-BOT-004 (остаётся P1).

## Получатели

Люди с записью на событие `practicum` в статусе, отличном от `cancelled`, у которых есть `telegram_id`.
Один человек — одно сообщение (дедуп по `people.id`). Люди без Telegram (пришли с сайта только с почтой) в рассылку
не входят — в предпросмотре отдельной строкой «Без Telegram, бот им не напишет: N».

## Команда

Только для `ADMIN_CHAT_IDS` (фильтр `IsAdmin` на уровне роутера, как в `admin.py`).

1. `/broadcast_practicum <текст>` (текст — всё после команды, может быть многострочным, с ссылками).
   Без текста — подсказка по использованию. Пустой текст после `strip()` и текст длиннее 4000 знаков — отказ с понятным
   сообщением (лимит Telegram — 4096).
2. Предпросмотр: сообщением владельцу ровно тот текст, который уйдёт (без разметки, без превью ссылок), и отдельной
   строкой: «Получателей: N. Уже получили это сообщение: K. Без Telegram: M.» + inline-кнопки «Отправить N» и «Отмена».
   Если получателей к отправке 0 — кнопка «Отправить» не показывается, пишем «Отправлять некому».
3. Текст ожидающей рассылки хранится в FSM-данных владельца (`state.update_data`, **без смены состояния**, чтобы не мешать
   режиму «Ответить на вопрос»); в `callback_data` — только короткий хеш текста (`bc:send:<hash8>`, `bc:cancel`).
   Если данных нет или хеш не совпал (бот перезапускался, текст заменён новой командой) — «Рассылка устарела, отправьте
   команду ещё раз».
4. «Отправить»: кнопки в предпросмотре убрать (`edit_reply_markup`), сразу ответить «Рассылка идёт…» и отправлять
   **в фоне** (`asyncio.create_task`, ссылка на задачу хранится, чтобы её не собрал GC), чтобы вебхук Telegram вернул 200
   сразу. В один момент идёт одна рассылка (`asyncio.Lock`); вторая в это время — «Рассылка уже идёт, дождитесь отчёта».
5. Отправка каждому: `bot.send_message(chat_id, text, link_preview_options=disabled)` без `parse_mode`;
   пауза между сообщениями `1/25` секунды (≤ 25 в секунду); `TelegramRetryAfter` — подождать `retry_after` и повторить
   (до 3 раз); `TelegramForbiddenError` (бот заблокирован) — статус `blocked`; прочие ошибки — `failed` (после 1 повтора).
6. Идемпотентность через таблицу `deliveries`: `kind = "broadcast:" + sha256(text)[:8]`, уникальность
   `(person_id, event_id, kind)`. Статусы `sent` и `blocked` при повторной отправке **того же текста** пропускаются,
   `failed` — повторяются (строка обновляется). Новый текст — новый `kind`. Запись в `deliveries` делается сразу после
   каждой отправки (а не пачкой в конце), чтобы падение посреди рассылки не приводило к дублям при повторе.
7. Отчёт владельцу после окончания: «Рассылка завершена: отправлено X, заблокировали бота Y, ошибок Z, пропущено
   (уже получили) W.» Если Z > 0 — добавить «Повторите команду с тем же текстом: отправятся только неполученные».
   Даже если задача упала с исключением — владелец получает сообщение «Рассылка прервана…» с числами на момент сбоя.
8. В меню команд владельца (`ADMIN_COMMANDS` в `setup.py`, `commands.*` в `texts.yaml`): `broadcast_practicum` —
   «Рассылка участникам практикума».
9. Логи: только `broadcast: hash=… recipients=… sent=… blocked=… failed=…` и внутренние id. Текст рассылки, имена, username и
   telegram_id — не логируем.

## Сервис (`app/services/broadcast.py`)

Логика без aiogram-хендлеров, чтобы её можно было вызвать и из будущего планировщика (TASK-BOT-004):
- `text_hash(text) -> str`;
- `collect_audience(session, event_code="practicum") -> Audience(recipients: list[Recipient], without_telegram: int)`;
- `already_delivered(session, event_id, kind) -> set[person_id]` (статусы `sent`, `blocked`);
- `send_broadcast(bot, text, *, event_code, kind, pause=1/25) -> BroadcastResult(sent, blocked, failed, skipped)`.

## Acceptance Criteria

- A1. `/broadcast_practicum` от не-админа не выполняется и уходит дальше как обычный текст (тест).
- A2. Админ: команда с текстом → предпросмотр с точным числом получателей (отменённые, без telegram_id и дубли не считаются) (тест).
- A3. «Отправить» → всем получателям ушло одно сообщение с этим текстом и отключённым превью ссылок; в `deliveries` строки
  `sent`; владельцу пришёл отчёт (тест).
- A4. Повторная команда с тем же текстом → «Уже получили: K», повторно никому не отправляется (тест). Новый текст → отправляется всем (тест).
- A5. Пользователь заблокировал бота → статус `blocked`, остальным уходит, отчёт честный (тест через `FakeSession.block_chat`).
- A6. Сбой отправки (не 403) → `failed`; повторная команда досылает только им (тест).
- A7. `TelegramRetryAfter` — повтор после паузы (тест с `pause=0` и подменой `asyncio.sleep`).
- A8. Устаревшая кнопка (другой текст/нет данных) не отправляет ничего (тест). Две подряд «Отправить» не дублируют (тест на lock/идемпотентность).
- A9. Пустой текст и текст > 4000 знаков отклоняются; 0 получателей — кнопки «Отправить» нет (тесты).
- A10. Логи не содержат текст рассылки и персональные данные (тест по `caplog`).
- A11. `ruff check .` и `pytest -q` зелёные на SQLite и на Postgres.

## Constraints

- Не менять модели и миграции (таблица `deliveries` уже есть).
- Цены, даты и ссылки в код и тексты не вписывать: текст рассылки приходит от владельца в команде.
- Токен только из окружения. ПД не в логах.
